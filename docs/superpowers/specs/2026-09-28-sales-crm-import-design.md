# Sales CRM workbook import design

Date: 2026-09-28
Status: approved for autonomous execution
Roadmap phase: C

## Intent

Turn the existing browser-side workbook parser into a workspace-scoped Sales
CRM import flow with arbitrary mapping, pre-commit validation, duplicate review,
atomic persistence, and visible source lineage.

## Decisions

- Reuse `parseUploadedWorkbook`; `.xlsx`, `.xlsm`, and `.csv` remain local to
  the browser and macros are never executed.
- Do not reuse the legacy `uploaded_files` tables or `uploaded-file-merge` Edge
  Function. They are owner-scoped and encode legacy HubSpot columns.
- Preview rows and validation stay in browser memory. Postgres stores normalized
  CRM records plus import metadata and row references, not raw workbook rows.
- A bounded Postgres RPC commits one import transaction. It validates workspace
  membership server-side and derives audit user IDs from `auth.uid()`.
- Company duplicate identity is normalized company name within a workspace;
  contact duplicate identity prefers normalized email; deal rows are created
  when a mapped deal name is present.
- Duplicate company/contact rows link to existing records and add lineage rather
  than silently creating copies. The result reports created, matched, skipped,
  and invalid counts.
- The source checksum is SHA-256 of the original file bytes. The stable Database
  ID is generated by `crm_source_imports` and shown with filename/sheet.

## Mapping and validation

Supported roles cover company name, industry, website, domain, company phone,
address, contact first/last/full name, email, contact phone, job title, deal
name, stage, amount, currency, owner, last call, and follow-up. Company name is
required for a row that creates or matches a company. Contact identity requires
a name or email. Amounts and dates must parse safely; formulas are treated as
plain cell values and imported HTML is never rendered.

The preview displays the first 25 normalized rows, per-row issues, and aggregate
valid/invalid/duplicate counts. Commit is disabled until mapping is valid and at
least one valid row exists.

## Security and limits

- Maximums remain 25 MB, 200 columns, and 20,000 rows at parse time.
- The commit RPC additionally caps the JSON row count and rejects unknown fields.
- Every query and write is workspace-scoped. Composite foreign keys retain the
  cross-workspace integrity established in Phase B.
- The RPC is `security invoker` with an empty search path, explicit membership
  checks, RLS enforcement, and execute permission only for `authenticated`.

## Verification

- Pure tests cover mapping, date/amount parsing, validation, deduplication, and
  summary generation.
- Migration contract and SQL tests cover membership denial, atomic creation,
  duplicate reuse, Database ID, and row lineage.
- Browser smoke covers sheet selection, mapping changes, preview, commit summary,
  and visible lineage without uploading the source workbook.
